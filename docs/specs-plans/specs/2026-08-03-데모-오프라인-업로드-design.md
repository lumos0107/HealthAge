# 데모 계정 오프라인 업로드 경로 — 설계

## 1. 배경

시연을 앞두고 있다. 노트북·PC·안드로이드 태블릿·폰을 가져가지만 **인터넷이 없을 수 있다.**

현재 업로드 탭은 데모 계정이든 실계정이든 무조건 백엔드를 호출한다.

- 사진을 고르면 즉시 `POST /uploads` (OCR) — `UploadScreen.tsx` `runOcr`
- 「확인한 값 저장하기」는 `POST /analyze` — `UploadScreen.tsx` `confirmSave`

백엔드가 없으면 **시연 도중 에러 토스트가 뜬다.** 백엔드를 노트북에서 띄우더라도 OCR은 `qwen2.5vl:7b` 비전 모델이라 한 장에 수십 초가 걸려 시연 시간에 맞지 않는다.

목표는 **업로드 → 인식 → 검수 → 저장 UX 전체를 네트워크 없이 끊김 없이 보여주는 것**이다. 분석 결과 데이터는 이미 앱 안에 있는 것을 쓴다.

## 2. 범위

**포함**

- 데모 계정(`root`/`1234`)에서 검진지 업로드 경로가 네트워크 없이 동작
- 시연에서 찍을 **검진 결과지 문서 1장** (2024년 회차 값)

**제외**

- 복약 파일 업로드 — 시연 시나리오에 없다. 기존 「예시 미리보기」가 이미 있고, 누르지 않으면 문제없다.
- 새 회차 추가 — 저장해도 회차 수는 9개 그대로다. (§3 참조)
- 실계정 동작 변경 — 한 줄도 바뀌지 않는다.

## 3. 결정된 요구사항

| 항목 | 결정 | 근거 |
|---|---|---|
| 저장 후 화면 | **성공 메시지만.** 회차는 9개 그대로 | 새 회차를 만들려면 그 회차의 분석 결과 한 벌을 백엔드로 생성해야 한다. 시연에 그만한 값이 없다 |
| 채워질 값 | **데모 인물(홍길동)의 2024년 회차 값** | 저장 후 분석 탭에 2024년이 최신으로 보인다. 값이 같아야 「올렸더니 이게 나왔습니다」가 앞뒤 맞는다 |
| 「읽는 중」 연출 | **1.5초** | 즉시 채우면 미리 넣어둔 값으로 보인다. 3초 이상은 시연 중 침묵이 길다 |
| 저장 후 이동 | **화면에 머문다** | 시연자가 직접 분석 탭을 누르는 편이 자연스럽고, 변경도 없다 |

## 4. 설계 — 앱

### 4.1 왜 전용 모듈로 분리하는가

세 가지를 검토했다.

- **화면 안에 직접 분기** — `UploadScreen.tsx`가 이미 640줄이다. 시연용 코드가 화면 로직에 섞이면 나중에 걷어내기 어렵다.
- **`health.ts`(API 계층)에서 분기** — 순수 API 계층이 앱의 로그인 상태를 알아야 한다. 전역 가변 플래그가 생겨 추적이 나빠진다.
- **전용 모듈 분리** ← 채택

채택 이유:

1. `uploadCheckupImage()`가 돌려주는 `RealOcrResult` 모양만 똑같이 만들면 **검수 화면·확신도 표시·저장 흐름이 그대로 동작한다.** 새로 그릴 화면이 없다.
2. 시연 코드가 파일 하나에 격리돼, 시연 후 **파일 삭제 + 3줄 되돌리기**로 완전히 사라진다.
3. React Native import가 없는 순수 TS라 **vitest로 테스트할 수 있다.** 이 프로젝트에서 테스트 가능한 코드는 순수 TS뿐이다.

### 4.2 새 파일 `frontend-mobile/src/demoUpload.ts`

```
demoOcrResult(): RealOcrResult
    2024년 회차 값을 백엔드 OCR 응답과 같은 모양으로 만든다. 순수 함수.

demoUploadCheckup(delayMs = 1500): Promise<RealOcrResult>
    delayMs 만큼 기다린 뒤 demoOcrResult()를 준다.

demoAnalyze(delayMs = 800): Promise<RealAnalyzeResult>
    delayMs 뒤 저장 성공 응답을 준다.
```

값은 **하드코딩하지 않고 `data.ts`의 `reports` 마지막 항목(가장 최근 회차)에서 파생시킨다.** 데모 데이터가 바뀌어도 앱이 저절로 따라간다.

다만 **결과지 HTML은 자동으로 따라가지 못한다.** 그래서 테스트가 「마지막 회차는 2024년이다」를 함께 검증한다(§6-1). 데모 데이터를 고치면 테스트가 깨지고, 결과지도 고쳐야 함을 그때 알게 된다.

`reports` 값 키와 `ocrTemplate` id가 다르므로 매핑이 이 함수의 실제 내용이다:

| `reports` 키 | `ocrTemplate` id | 비고 |
|---|---|---|
| `glucose` | `fbs` | |
| `hemoglobin` | `hb` | |
| `triglyceride` | `tg` | |
| `totalCholesterol` | `total_cholesterol` | |
| `urineProtein` | `urine_protein` | `1` → 문자열 `'정상'`로 변환 |
| `sbp` `dbp` `ldl` `hdl` `ast` `alt` `ggt` `creatinine` `height` `weight` `waist` | 같은 이름 | |
| `bmi` | 없음 | 앱은 키·몸무게로 계산한다. 결과지에는 인쇄한다 |

`meta.exam_date`는 회차의 `date`, `meta.hospital`은 `hospital`에서 가져온다.

`demoAnalyze()`의 `medications_known`은 **`true`로 둔다.** `false`면 복약자료 업로드를 유도하는 안내가 뜨는데, 복약은 시연 범위 밖이라 흐름만 길어진다.

`RealAnalyzeResult`의 나머지 필드(`basic_report`·`comprehensive`·`recommendations`)는 **빈 객체로 둔다.** `confirmSave`는 `medications_known`과 `warnings`만 읽고 나머지는 쓰지 않는다.

### 4.3 `UploadScreen.tsx` — prop 1개 + 분기 2줄

```
runOcr:       demoMode ? await demoUploadCheckup() : await uploadCheckupImage(...)
confirmSave:  demoMode ? await demoAnalyze()       : await analyzeCheckup(ocrToSend, true)
```

나머지는 손대지 않는다. `ocrRaw`가 정상 모양으로 채워지므로 `requestSave`의 `usingExample || !ocrRaw` 차단(`UploadScreen.tsx:203`)을 그대로 통과한다.

### 4.4 `App.tsx` — 1줄

`<UploadScreen ... demoMode={isDemoAccount} />`

`isDemoAccount`(`= loggedIn && demoMode`)는 더미 데이터를 보여줄지 판단하는 **기존 게이트 그대로**다. 실계정으로 새어나갈 경로가 새로 생기지 않는다.

### 4.5 변경 총량

새 파일 2개(모듈·테스트). 기존 파일 2개에서 — `UploadScreen.tsx`는 prop 선언과 분기 2줄, `App.tsx`는 1줄. **새 의존성 없음.**

## 5. 설계 — 검진 결과지

`tools/demo_checkup_2024.html` — **HTML 한 장.** 브라우저에서 인쇄(PDF) 또는 캡처해 쓴다. 의존성이 0이고 값을 고치기 쉽다.

- A4 세로, 공단 일반건강검진 결과통보서 형태. 레이아웃은 `WITHUS/테스트검진지_마스킹/general_01_p1.png`를 참고한다
- §3의 값 18개 + BMI를 인쇄한다
- `@media print` 로 인쇄 여백·배경을 잡는다

**상단에 「시연용 예시 — 실제 검진 결과가 아닙니다」를 눈에 띄게 넣는다.**

기관명이 「서울대병원 강남센터」로 실존 병원이다. 앱 화면에 뜨는 것은 이미 그러하니 상관없지만, 종이는 앱 화면보다 진짜 문서처럼 보이고 시연장에서 돌려볼 수도 있다. 표기를 넣는 쪽이 `data.ts`를 건드리지 않아 간단하다.

## 6. 테스트

`frontend-mobile/src/demoUpload.test.ts` (vitest). 기존 `ocrFields.test.ts`가 `api.ts`를 모킹하는 방식을 그대로 따른다.

1. `demoOcrResult()`의 `meta.exam_date`가 `'2024-03-15'`, `meta.hospital`이 `'서울대병원 강남센터'`다 — 결과지 HTML과 앱이 어긋나면 여기서 깨진다
2. `measurements`가 2024년 회차의 값 전부를 `ocrTemplate` id로 담는다
3. `urineProtein: 1`이 `'정상'`으로 변환된다
4. **`ocrResultToFields(demoOcrResult().ocr)`에 빈 값이 없다** — 화면에 실제로 채워지는지 확인하는 핵심 검증. 검진일·기관 포함
5. `demoUploadCheckup(0)`이 `demoOcrResult()`와 같은 값을 준다

TDD로 진행한다. 테스트를 먼저 쓰고 실패를 확인한 뒤 구현한다.

## 7. 안전장치

- 데모 경로는 `isDemoAccount` 하나로만 열린다. 이 값은 이미 앱 전체에서 더미 노출을 통제하는 게이트다
- `demoUpload.ts`는 아무 것도 네트워크로 보내지 않는다
- 실계정 코드 경로는 한 줄도 바뀌지 않는다

`App.tsx:138-140`의 원칙 — *"검사하지 않은 항목을 검사한 것처럼 보여주지 않는다"* — 과 충돌하지 않는다. 데모 계정에 이미 더미 9개 회차를 보여주고 있고, 이 변경은 같은 게이트 안에 머문다.

## 8. 시연 후 걷어내기

1. `frontend-mobile/src/demoUpload.ts` 삭제
2. `frontend-mobile/src/demoUpload.test.ts` 삭제
3. `UploadScreen.tsx` — `demoMode` prop과 분기 2줄 되돌리기
4. `App.tsx` — `demoMode={isDemoAccount}` 1줄 되돌리기
5. `tools/demo_checkup_2024.html` 삭제

## 9. 이 문서가 다루지 않는 것

시연 준비의 나머지는 별도다.

- **APK 빌드** — Windows 260자 경로 제한으로 실패한다. `subst`로 가상 드라이브를 만들어 경로를 줄이는 것이 해법이다
- **노트북 웹 시연** — `npx expo export -p web`이 성공한다. `dist/`를 정적 서버로 띄우면 된다(절대경로 참조라 `file://`로는 안 열린다)
- **홈 「빠른 이동」 4버튼** — 외부 사이트라 오프라인에서 깨진다. 시연 중 누를지 판단 필요
