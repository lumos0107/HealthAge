### 13. `rarity`는 희귀도가 아니었다 (2026-07-28 발견·수정)

`calculate_group_rarity()`는 **이름과 달리 희귀도를 계산하지 않는다.**
사용자가 속한 임상·생활습관 집단군을 나열하고 **개수만 세서** 해석 문구를 붙일 뿐이다
(`gender`·`age`·`year`를 인자로 받지만 **본문에서 한 번도 쓰지 않는다** — 원래 인구 대비
희귀도를 계산하려다 만 흔적). 모집단 빈도·백분위 계산은 어디에도 없다.

```
임상군 0개 → "임상 위험 요인 없음 (건강 상태)"   3개 → "다중 위험 요인 (의료 상담 권장)"
       1개 → "단일 위험 요인 (관리 필요)"        4개+ → "고위험 패턴 (즉각 의료 진료 권장)"
       2개 → "복합 위험 요인 (적극 관리 필요)"
```

**그래서 생긴 모순**: 카드 제목이 "이 조합의 희귀도", 하단 면책이 "드물다고 더 위험한 건
아니다"인데, 정작 본문은 **"고위험 패턴 (즉각 의료 진료 권장)"**을 출력했다.
바로 위에서 진료를 권하고 아래에서 위험하지 않다고 말하는 셈이었다.

**원인**: 24번 §7-2의 항목명("`rarity` 희귀도 노출 — 희귀≠위험 프레이밍 동반")을 그대로 받아
**백엔드가 실제로 무엇을 계산하는지 확인하지 않고** 카드를 만들었다.
→ **24번 §2의 교훈("코드 주석이 아니라 호출 경로를 따라가서 확인해야 한다")을 그대로 반복했다.**

**수정**: 제목 "해당하는 위험군", 면책 "집단군의 개수를 센 참고 정보이며, 진단이 아닙니다."
필드명이 왜 `rarity`인지 코드 주석으로 남겼다. 백엔드는 손대지 않았다(앱 영향 없음).
→ 진짜 희귀함에 가까운 지표는 **조합그룹 카드의 O/E 배수 + 모집단 표본 수**다.

> ### ⚠️ 교훈 — 24번의 교훈이 이번에도 그대로 통했다
> 24번 §3: *"더미로 검증했더니 통과했다는 건 위험신호"*.
> 이번엔 아예 **웹에 더미 모드를 만들지 않고** 전 검증을 실계정(`webdemo40680`)으로 강제했다.
> 그 결과 #1·#5처럼 **첫 실사용에서야 드러나는 결함**이 개발 중에 잡혔다.
>
> 추가 교훈: **구현자와 리뷰어를 분리하니 12건이 나왔다.** 같은 사람이 짜고 검토하면
> 자기 가정을 다시 의심하지 못한다. #2·#3·#5는 태스크 리뷰를 전부 통과한 뒤

## 5. Git 브랜치 구성 (이번 작업에 신설)

머지 후 **컴포넌트별 브랜치 3개**를 만들어 푸시했다. 전부 `1eef6ca`에서 출발.

```
main       ← 통합 지점
front-app  ← 모바일 앱 (frontend-mobile/)
front-web  ← 웹 (frontend/)
backend    ← 백엔드 (backend/)
```

> ⚠️ **운용 주의**: 한 저장소를 4개 브랜치가 공유한다. `backend`에서 API를 고치면
> `front-web`은 머지해 오기 전까진 못 쓴다. 이번 작업의 Task 1·12가 그 예로,
> **백엔드와 웹을 동시에 고쳐야** 동작했다 — 브랜치가 갈려 있었으면 각각 반쪽이었다.
> → **작업이 끝날 때마다 `main`으로 합치고, 다시 `main`을 각 브랜치로 당겨오는** 흐름을 지킬 것.

로컬 잔여 브랜치: `web-full-rewrite`(main에 흡수됨) · `feat/web-real-api`(예전 미완). 정리 가능.

### 현재 브랜치 상태 (⚠️ 갈려 있음 — 머지 필요)

```

front-app  2e17136   ← §5-1 eGFR 버그 + §5-2 집단군 요약
```

**아직 main으로 합치지 않았다.** 위 운용 주의대로 각 브랜치 작업을 `main`에 합치고

```
앱  frontend-mobile/src/health.ts:589   sex: sex === 2 ? 'female' : 'male'   ← 버그
웹  frontend/src/api/endpoints.ts:98    sex: sex === 2 ? 'F' : 'M'           ← 고침
```

백엔드 `app/renal/gfr.py`의 `Sex` enum은 **`'M'`/`'F'`만** 받는다.
`'male'`/`'female'`을 보내면 Pydantic 검증에서 **422**가 나고,
`fetchEgfr`의 `catch`가 그걸 삼켜 **화면에는 에러도 없이 신장 기능 섹션이 통째로 사라졌다.**

**API 레벨 확정** (로컬 백엔드 직접 호출):
| 요청 | 결과 |
|---|---|
| `{"serum_cr":0.9,"age":52,"sex":"male"}` | **HTTP 422 — 실패** |
| `{"serum_cr":0.9,"age":52,"sex":"M"}` | `{"egfr":102.8,"stage":"G1", …}` **정상** |

**에뮬레이터 실화면 확인** (webdemo40680, emulator-5554):
```
🩺 신장 기능
   신장 기능 (eGFR)   94 mL/min/1.73㎡   [G1 · 정상 또는 높음]
   약물 용량 참고 (CrCl)  100.3 mL/min · Cockcroft-Gault  [정상 범위]
```
수정 전엔 이 섹션이 **없던 자리**다. 체중 반영 CrCl까지 함께 복구됐다.

> **교훈**: 웹을 만들면서 처음 실사용한 엔드포인트에서 앱의 묵은 버그가 드러났다.
> `catch { return null }`이 실패를 삼키면 **기능이 조용히 사라지고 아무도 모른다.**
> 앱에서 오래 안 보이던 기능이 있으면 "미구현"이 아니라 **"조용히 죽은 것"**을 먼저 의심할 것.

## 5-2. 앱에 집단군 요약 추가 — "간결하되 깊이 있게"

사용자 설계 원칙:
> "일단 앱에 모든 기능을 다 들어가게 하고 **배치나 뎁스를 바꿔**,
> 일반적으로는 간결한데 **확인하고 싶은 사람은 확인할 수 있게** 할 것 같음"

`rarity`(집단군 개수)를 앱에도 넣되, **새 카드를 만들지 않았다.**
앱에는 이미 `집단군 판정` 카드가 13개 항목을 전부 보여주고 있어서
카드를 새로 만들면 **같은 내용이 두 번** 나온다. 대신 그 카드 **맨 위에 요약 줄**만 얹었다.

```
집단군 판정
검진 수치와 복용 약물을 함께 반영해 판정한 결과예요.
┌────────────────────────────────┐
│ 임상 5개 · 생활습관 0개에 해당     │  ← 추가한 요약
│ 고위험 패턴 (즉각 의료 진료 권장)  │
└────────────────────────────────┘
임상
고혈압        비해당
고혈압 전단계   해당
…             (상세 13줄 그대로 유지)
```

대충 보는 사람은 두 줄로 끝내고, 파고들 사람은 아래 13줄을 본다.
**웹과 앱의 라벨도 통일**했다 — 둘 다 희귀도가 아니라 집단군 개수로 표기(§3-13).

**검증**: 에뮬레이터 실화면 확인. `rarity`가 주입 이후 저장분에만 있어
웹에서 검진 1건을 임시 저장 → 앱에서 요약 줄 확인 → **삭제해 실계정을 2023·2024로 원상복구**했다.
앱 `.env`도 로컬 검증용으로 바꿨다가 **터널 주소로 원복** 완료.
